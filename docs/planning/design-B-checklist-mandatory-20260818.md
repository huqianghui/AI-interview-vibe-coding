## Problem Statement

管理员建了一套题（如 `hello, how are you` / `what's your name` / `how old are you`），跑完
面试拿到的报告是 **"覆盖率 0% / 占位评分 —— 尚未按 SOP 评分"**（stub scoring）。根因已核实：

- 评分（F4）唯一依据是每题绑定的 **Checklist**（`scoring_service.py:84` → `get_default_checklist`）。
  题没有 checklist → 返回 `None`（`:85-86`）→ state machine 落到按长度给的 stub 行
  （`state_machine.py:220-222`）→ 整份报告 `is_stub = not any_graded`（`:266`）。
- 现状建题（`admin.addBankQuestion`）**不建 checklist**；checklist 唯一产生途径是管理员在
  `/admin` 手动点 **"Draft from SOP"**（`AdminPage.tsx:436`）。
- 那个入口还极难发现：要先点"看起来不可点"的题目文字（`AdminPage.tsx:350`，`subtle` 按钮）
  才在页面最底部冒出 Checklist 卡片。
- **更关键**：即使点开，UI 也**只能 Draft / Re-draft**，没有任何人工编辑控件。后端
  `PUT /admin/checklists/{id}/items`（`admin_checklist.py:102`）和 API 客户端
  `editChecklistItems`（`admin.ts:125`）**都已存在**，但 `AdminPage.tsx:413-420` 的列表是
  **纯只读展示** —— edit 能力从没接进 UI（文件顶部注释 `:6` 却写着 "edit item weights + text"）。
- 对没有 SOP 的闲聊题，"Draft from SOP" 检索不到内容 → AI 起草返回空 → checklist 永远空 →
  永远 stub。管理员**没有任何办法**给这类题配一份评分标准。

一句话：**系统里"人工定义/修正评分标准"这条路径根本不存在，且非闲聊题也可能因没点过 draft
而落成占位评分。** 交付给客户的题库随时可能是"占位评分"，直接破坏"评分一致、可复现"的硬约束。

## What Makes This Cool

**不变式：每道题恒有一份非空、可编辑的 checklist。** 建题那一刻后端就 AI 生成一份初值
（从题目本身出，不强依赖 SOP），管理员想改就直接在题下面编辑、保存即重新归一到 100。
"占位评分"这个悬空状态从此不该出现在任何正常建出来的题上 —— 评分链路默认就是通的，
而不是需要管理员记得去点一个藏起来的按钮。

而且大部分零件已经就位：drafting prompt 早已把题目文本喂给 LLM（`checklist_service.py:56`），
编辑后端 + API 客户端都现成。这次主要是**补齐无 SOP 时的可靠产出** + **把编辑控件接进 UI** +
**在建题流程里挂上自动生成**，而不是从零造。

## Constraints

- **交付级质量**：评分必须一致、可复现。checklist 是评分口径的唯一载体，因此"恒有且非空"
  是本功能的成败点。
- **P3 候选人边界（硬红线）**：checklist / rubric / weight / source_quote 绝不能进入任何
  候选人可见 API。编辑与自动生成都发生在 admin-only 路径；候选人投影
  （`api/interview.py`）已隔离，不动它。
- **权重和恒为 100**：编辑保存复用现有 `normalize_weights`（最大余数法），`forbidden` 恒 0。
  `update_items`（`checklist_service.py:175`）已做归一，接线即可。
- **零 Azure 可测**：AI 生成走现有 LLM adapter（mock provider 在 CI 里可跑）；建题自动生成
  的**触发与落库**必须在 mock provider 下 CI 全绿。
- **不破坏现有面试流**：state machine / 报告 / 候选人流一律不改；空 checklist 仍可跑（只是
  评分退化），本功能只保证正常建题时非空。
- 语言：仅中英文，禁日文（贯穿 UI 文案）。

## Premises

- **P1（已确认）**：每道题**必须**有 checklist，默认由 AI 生成，人工可修改。
  → 建题时后端自动生成，不再依赖管理员记得手点。
- **P2（已确认，已核实半就绪）**：AI 生成**从题目本身**出，不强依赖 SOP。
  `_build_draft_prompt`（`checklist_service.py:47-57`）**已经**把 `question.text` 传给 LLM，
  且 SOP 空时写 `(no SOP passages retrieved)`。当前 prompt 措辞是 "grounded in the SOP"，
  无 SOP 时 LLM 可能因"没材料"而返回空 → 本功能改 prompt，让无 SOP 时也可靠产出通用评分要点。
- **P3（已确认）**：checklist 为空时可"再用 AI 生成默认"。这与 P1 是同一条 from-question
  生成路径，UI 上表现为一个"重新生成"动作。
- **P4（本设计新增，需你确认——见 Open Q1）**："必有值"落到多强？倾向：**建题自动生成 +
  非空兜底**，但**不阻断**面试（空仍可跑，只是标提醒），把破坏面。风险降到最低。
- **P5（已确认，范围）**：admin 页 Tab 化（三个顶级 Tab + 共享导航）**本次不做**，作为随后
  独立 PR。本设计只做 checklist 侧。
- **P6（已核实，范围）**：SOP 语料**没有前端上传入口**——后端 `POST /admin/sop/documents`
  （F1，已注册、admin-only）存在，但 `frontend/src` 里 **零** `/admin/sop` 调用（已 grep 核实）。
  注意 admin/agent 页里的 "knowledge base/source" 是 **F5 的 per-persona Foundry IQ KB**
  （面试官 agent 面试中实时检索），**不是** F1 的 SOP 语料，两者不同。**推论**：checklist
  生成**不能**寄托于"先传 SOP"（那条路 UI 走不通）→ 更加坐实 P2"AI 从题目生成、SOP 可选"
  是唯一可行默认。**SOP 前端上传 UI 缺失是独立的 F1 前端缺口，明确 out of scope**，记为单独
  backlog（与 Tab 化 PR 同类），本设计不碰。

## Approaches Considered

### Approach A：建题自动 AI 生成 + 接线编辑 UI（推荐，已锁定方向）

三处改动，从后往前：

**1. AI 生成不再强依赖 SOP（`checklist_service.py`）**
- 改 `_build_draft_prompt`：措辞从"grounded in the SOP"改为"为这道面试题起草一份通用评分
  checklist；若提供了 SOP 段落则据其加分，否则仅凭题目本身给出合理的 required/recommended/
  forbidden 要点"。仍要求 JSON-only、kind 合法、权重约 100。
- 强化非空兜底：现有 `if not items: fallback_items_from_points(...)`（`:110-111`）在
  `expected_points` 也为空时仍会产出空。新增一条**最终兜底**：若走完 LLM + expected_points
  仍为空，则合成一条通用 `required` 项（如"回答切题、完整、准确"，w=100），保证 checklist
  非空。→ "AI 从题目生成"为主，"固定占位项"为最终保险（对应你选的"AI 从题目生成"+ 系统级
  非空保证）。

**2. 建题时自动生成（`question_service` + `admin_questions.py`）**
- `admin.addBankQuestion` 落题后，同步调用 `checklist_service.draft_checklist(question_id)`
  生成默认 checklist。放在同一请求里（建题成功即返回带 checklist 的题），或建题后由前端串一个
  draft 调用——**倾向后端一处做**（前端少一次往返、不变式在服务端成立）。
- 失败处理：AI 生成因 provider 报错失败时，题仍建成（不因评分标准生成失败而阻断建题），
  记一条 warning；此时 checklist 为空，管理员可在编辑器点"重新生成"。（这是 P4"不阻断"的
  体现。）

**3. 接线编辑 UI（`AdminPage.tsx`）**
- 把 `:413-420` 的只读 `<li>` 列表换成可编辑行：每条 rubric 一行 `kind` 下拉
  （required/recommended/forbidden）+ `text` 输入 + `weight` 数字输入 + 删除按钮；
  底部"添加一条"；一个"保存"按钮调 `editChecklistItems(checklist.id, items)`
  （`admin.ts:125`，已存在）→ 后端 `update_items` 重新归一到 100 → 回填。
- 保留现有"Draft from SOP / Re-draft"按钮，语义并入"重新生成（AI）"。
- 可发现性修复（顺手）：题目行的 checklist 入口从"点题目文字"改为一个明确的"评分标准 /
  Rubric"按钮，或在题目行显示 checklist 状态（"✓ N 项 / ⚙ 未配"）。

**落库与归一**：编辑保存复用 `update_items`（已归一到 100、drop 非法 kind、`forbidden`→0）。
建题自动生成复用 `draft_checklist` → `normalize_weights` → `_persist_draft`（demote 旧 default）。

工作量：中小。风险：低（后端编辑/归一/生成都现成，主要是 prompt 调整 + 建题挂钩 + 前端表单）。

### Approach B：仅接线编辑 UI，不做建题自动生成

只把编辑控件接进 UI，建题仍不自动生成 checklist。**不选** —— 无法满足 P1"每题必有"，
你那 3 道题依然要手动逐题点生成，占位评分仍会出现在忘了配的题上。

### Approach C：阻断式强约束（空 checklist 禁止 set-default）

在 B 之上，任一题 checklist 为空则禁止该 bank set-default。**本次不选**（你选了"为空可再 AI
生成"而非阻断）；留作将来"交付前校验"可加的更严档位。

## Recommended Approach

**Approach A**：建题自动 AI 生成（从题目本身，SOP 可选）+ 系统级非空兜底 + 把已存在的
`editChecklistItems` 接进 AdminPage 编辑表单 + 顺手修 checklist 入口可发现性。

理由：直接命中"每题必有可编辑 checklist"的原则；大部分后端/API 已就绪，改动集中在 prompt、
建题挂钩、一个前端表单；全程 mock provider 可测、零 Azure；不碰候选人流与 P3 边界。做完后
你那 3 道闲聊题建出来就带评分标准，报告不再是占位评分。

## Open Questions

1. **"必有值"落到多强（P4）**：倾向"建题自动生成 + 非空兜底，但不阻断面试（空仍可跑、
   仅标提醒）"。若你要更强（空则禁止 set-default），走 Approach C 档位。**默认按不阻断做。**
2. **自动生成放后端还是前端串**：倾向后端在建题请求里一处完成（不变式服务端成立、前端少一次
   往返）。若担心建题响应变慢（多一次 LLM 调用），可改为建题后前端异步补一次 draft +
   loading 态。**默认后端一处做**，若延迟明显再改异步。
3. **建题自动生成失败的 UX**：AI provider 报错时题照建、checklist 空、记 warning，管理员在
   编辑器点"重新生成"。是否需要在题列表显式标红"评分标准生成失败"？**默认标一个中性的
   "⚙ 未配评分"状态**，不区分"没生成"与"生成失败"。

## Success Criteria

- 新建一道题（含闲聊题如"how are you"），**建完即带一份非空 checklist**（AI 从题目生成）。
- 管理员在题下面能**手工加/改/删** rubric 条目、改权重、保存 → 权重和显示 100。
- 对一道题手工配好 required 项后跑面试 → 报告 `is_stub=false`、真覆盖率、真等级
  （不再"占位评分"）。
- checklist 为空时（如生成失败），点"重新生成"能再出一份非空 checklist。
- P3 隔离保持：候选人 API 仍无任何 rubric 字段（复用现有 P3 E2E 断言）。
- 现有 411 后端 / 102 前端测试全绿；新增：无 SOP 时 draft 非空、建题自动挂 checklist、
  编辑保存归一到 100、非空兜底。

## What I noticed about how you think

- 你没有接受"上传模板批量导入"作为唯一答案，而是回头盯住一个更基础的问题："单题现在到底
  能不能人工配评分？" —— 你在为最小可用路径把关，而不是先追大功能。
- 你把"每题必有 checklist"定成一条**原则**，而不是在我给的两个后端形状里挑一个。你要的是
  不变式，不是补丁 —— 这决定了正确的实现是"建题即生成"，而不是"给漏配的题补个入口"。
- 你选"AI 从题目生成"而非"固定占位项"，说明你要的初值是**对这道题有意义的**，哪怕要多调一次
  LLM。你在为管理员省"从零写 rubric"的力，同时不牺牲初值质量。
