# SOP 知识处理与评估机制说明（客户交底文档）

> 面向对象：客户业务/评审方。
> 目的：说清楚"SOP 原文 → 切块（chunk）→ 检索（RAG）→ 评价标准（checklist）→ 打分"这整条链路到底是怎么工作的，评估时到底参照了什么，为什么这样设计。
> 说明：本文所有描述均以当前代码实现为准（非规划、非设想）。关键实现文件已在文中标注，便于双方对照。

---

## 0. 一句话总览

SOP 原文在**上传阶段**被提取、切块、建立索引；在**编制评价标准（checklist）阶段**通过检索（RAG）被用来生成"逐条评分标准 + 原文出处"；到了**给候选人答案打分阶段**，系统评委只依据这套已经固化的评价标准来判分，**不再回看 SOP 全文，也不再做检索**。

这样做的核心目的：让每一个分数都**可解释、可复现、可申诉、可追溯到原文**。

---

## 1. 全链路总览

```
① 上传 SOP 原文（PDF / Word / PPT / Markdown / txt）
        │  提取纯文本
        ▼
② 切块 chunk（约 512 字/块，带 64 字重叠，尽量在段落处断开）
        │  每块保留：页码/章节标签、结构路径
        ▼
③ 建立索引（进入知识库 / 向量检索）
        │
        ▼
④ 编制评价标准 checklist（管理员操作，每题一次）
        │  用问题去检索 SOP 相关片段（RAG）
        │  大模型据此起草：必答项 / 建议项 / 禁止项 + 权重 + 原文引用
        │  管理员可人工编辑、增删、调权重
        ▼
   【评价标准固化下来，成为这道题的评分依据】
        │
        ▼
⑤ 候选人答题
        │
        ▼
⑥ 打分（对每道题，逐条对照评价标准判定）
        │  评委看到：问题 + 评价标准（含每条的简短原文引用）+ 候选人回答
        │  ❌ 不注入 SOP 全文  ❌ 不做检索
        │  逐条判 4 态 → 按权重算分 → 定档
        ▼
⑦ 生成报告（每条判定都能指回它对应的评价标准和 SOP 出处）
```

**关键分界线**：SOP 原文（chunk / RAG）只作用到第 ④ 步（编制标准）；第 ⑥ 步（打分）只用第 ④ 步产出的评价标准。

---

## 2. 逐步拆解

### 步骤①②③：SOP 原文的提取、切块与索引

**发生时机**：管理员上传 SOP 文件时（一次性）。

- **提取**：按文件类型解析成纯文本。支持 PDF、Word（docx）、PPT（pptx）、Markdown（md）、纯文本（txt）。
  （实现：`backend/app/sop/extraction.py`）
- **切块（chunk）**：把长文本切成一块块约 **512 个字符**的片段，相邻块之间有 **64 字符重叠**，并尽量在换行/段落处断开，避免把一句话从中间切断。
  - 为什么要切块：① 长文档无法整篇喂给大模型（有上下文长度限制）；② 检索时可以精确定位到"是文档的哪一小段"，从而支撑"引用+页码"的溯源。
  - 每一块都会保留 **页码/章节标签**（如"第 3 页"、"3 > 安全 > 3.2"），这是后面所有"引用可点回原文"能力的基础。
  （实现：`backend/app/models/sop.py` 中的 `SopChunk`；切块逻辑在 `extraction.py` 的 `chunk_text`）
- **索引**：切好的块进入检索库（生产环境为 Azure Foundry IQ / AI Search 知识库），供第④步检索。

> **原文存在哪里？**
> - 完整原文文件本身存在对象存储（Blob），数据库里只存一个"存储指针"（`SopDocument`），**数据库不保存原文全文**。
> - 数据库里能被系统直接读到的原文，是**切块后的片段**（`SopChunk.content`），带页码标签。
> - 设计约束：SOP 原文**绝不直接返回给候选人**，候选人只可能在报告里看到经服务端中转的、简短的引用片段。

### 步骤④：编制评价标准 checklist（RAG 在这里发挥作用）

**发生时机**：管理员为某道题"生成/重新生成评价标准"时（每题一次，可反复重来、可人工编辑）。

流程：
1. **检索（RAG）**：用这道题的题干去知识库检索最相关的 SOP 片段（默认取 top 3）。
   （实现：`checklist_service.draft_checklist` → `retrieval.retrieve_citations(question.text, max_citations=3)`）
2. **大模型起草**：把检索到的 SOP 片段作为依据，让大模型起草出一组评价标准条目，每条包含：
   - **kind（类型）**：`必答项 required` / `建议项 recommended` / `禁止项 forbidden`
   - **text**：这条标准的文字描述
   - **weight（权重）**：一道题所有条目的权重之和归一化到 **100**
   - **source_quote（原文引用）**：这条标准对应的一小段 SOP 原文（用于溯源展示）
   - **source_page / source_document_id**：指回原文的页码与文档
   （实现：`checklist_service._build_draft_prompt` + `_persist_draft`；数据模型 `backend/app/models/checklist.py`）
3. **人工把关**：管理员可在编辑器里增删条目、改文字、调权重、改类型。评价标准是**管理员最终确认**的，不是大模型说了算。
   （实现：`checklist_service.update_items`）

> **兜底逻辑（保证"每题都有可用的评价标准"）**：
> - 如果没有配置 SOP 或没检索到片段，大模型仍会**仅凭题干**起草一份合理的评价标准（此时 `source_quote` 为空）。
> - 如果大模型没产出可用条目，则退回用题目预设的"期望要点（expected_points）"，每条转成一个必答项。
> - 如果连期望要点都没有，则合成一条通用必答项"回答切题、完整、准确"。
> - 也就是说：**评价标准永远非空**，绝不会退化成"仅按回答长度打分"的粗糙模式。

### 步骤⑤⑥：打分（评估的核心——这里**不看**原文全文）

**发生时机**：候选人每回答完一道题。

**评委（大模型）在打分时收到的，只有三样东西**：
1. 问题题干
2. 该题的评价标准列表（每条：类型 + 文字 + **如果有的话**那一小段 `source_quote` 原文引用）
3. 候选人的这条回答

（实现：`scoring_service._build_scoring_prompt`，第 39–57 行）

**明确地说**：打分环节**不注入 SOP 全文**，也**不再触发检索/RAG**。我们已在代码层核对：打分函数 `score_answer_against_checklist` 全程只读评价标准表，然后调用大模型；不涉及任何知识库检索或 SOP 片段拉取。

评委要做的事：**对每一条评价标准**，判定候选人的回答属于以下 4 种状态之一：

| 状态 | 含义 | 计分 |
|---|---|---|
| `met` 符合 | 完全满足这条标准 | 该条权重 × 1.0 |
| `partially_met` 部分符合 | 部分满足 | 该条权重 × 0.5 |
| `not_met` 未符合 | 没满足 | 0 |
| `violated` 违规 | 触发了"禁止项" | 0，且触发警告 |

评委还需给出每条判定的 `rationale`（判定理由）和 `answer_quote`（候选人回答里对应的原话片段），供报告展示。

### 评分的"护栏"（保证分数可信、不虚高）

打分不是大模型说多少就是多少，系统有一层**纯规则护栏**（不依赖大模型，`backend/app/interview/scoring_engine.py`）：

1. **空答/过短答**（少于 20 字）→ 强制所有条目 `not_met`，杜绝"随便说两句拿高分"。
2. **禁止项被触发** → 强制判为 `violated` 并告警，无论回答里还说了什么好话。
3. **凭空捏造的条目**（大模型给了一个评价标准里没有的条目）→ 丢弃并记录日志，评委不能对不存在的标准打分。
4. **漏判**（大模型没给某条标准的判定）→ 抛错并**自动重试一次**，绝不因漏判而虚增覆盖率。

### 权重计分与定档

- **单题得分** = Σ（各条权重 × 该条得分系数）/ 总权重 × 100，四舍五入到 0.1。
- **档位（报告头条结论）**：
  - ≥ 70 分 → **符合预期（Meets Expectations）**
  - 40–69 分 → **需要改进（Needs Improvement）**
  - < 40 分 → **不符合（Does Not Meet）**
- **关键错误封顶**：若触发了**非提示性**的禁止项（确认的关键错误），无论分数多高，档位最高只能到"需要改进"。
  （提示性/待确认的禁止项只做披露，不封顶——用于"已知但尚未定论的冲突"这类情况。）
  （实现：`scoring_engine.cap_outcome`）

### 步骤⑦：报告与溯源

报告里每一条判定都能指回：它对应哪条评价标准 → 该标准的 `source_quote` 原文引用 → 页码/文档。这就是"每个判分都能追溯到 SOP 原文"的能力来源。

## 3. 直接回答客户的核心问题

**问：评估时是否参照 SOP 原文件（完整 Markdown 内容）作为参照？还是剥离出问题和评价标准后就不再参考原文了？**

**答：属于后者。** 一旦 SOP 被加工成"问题 + 评价标准"，打分环节就**只依据评价标准**，不再回看 SOP 全文、也不再检索。SOP 原文的作用集中在**编制评价标准**那一步（检索出相关片段辅助生成标准，并保留简短引用做溯源）。

**为什么这样设计（这是优点，不是缺陷）：**

| 价值 | 说明 |
|---|---|
| **公平一致** | 所有候选人对同一道题，用的是同一套固定标准，不会因为原文被截取/理解不同而波动。 |
| **可复现** | 同样的回答、同样的标准，得分稳定，可重跑验证。 |
| **可申诉/可解释** | 扣分能精确到"漏了第几条必答项"，能对被考核人讲清楚。 |
| **成本与速度** | 不必每次答题都把整篇 SOP 喂给大模型，token 成本与延迟可控（语音场景尤其重要）。 |
| **防泄题** | SOP 原文不进打分环节，泄漏面更小。 |
| **可追溯** | 评价标准仍保留原文引用与页码，报告里可点回原文。 |

**这样设计的取舍/客户可能关心的点：**

- 打分的"上限"取决于**评价标准编得好不好**。如果编制标准时漏掉了 SOP 里的某个要点，打分阶段不会自动把它补回来。
- 这正是我们保留**人工编辑**与**可反复重生成**评价标准的原因：标准的质量由管理员最终把关。
- 针对这一点，我们已经落地两项增强，且**不牺牲上面的公平性/可复现性**：评估时让评委看到每条标准背后**更完整的原文段落**（C，默认开启），并提供一个**可选的原文覆盖度体检**（D，评估时可勾选、默认关闭）——详见下一节。

## 4. 原文增强：C（已默认开启）+ D（评估时可勾选，默认关）

> 下面两项**已经实现并合入主线**。C 默认生效、无需任何操作；D 是评估时的一个勾选项，默认关闭。
> 关键前提：**两者都不改变计分逻辑**——分数始终是"评价标准 + 4 态判定 + 权重"的确定性函数，
> 公平/可复现/可申诉的特性完全保留。

| 方案 | 状态 | 做法 | 取舍 |
|---|---|---|---|
| **A. 全文注入打分** | ✗ 未采用 | 打分时把整篇 SOP 塞进评委 prompt，让其自由裁量 | 最贴近"参照原文"字面诉求，但**牺牲可复现性、架空权重制、成本/延迟高、有泄题面**。**不推荐。** |
| **B. 相关片段注入打分** | ✗ 未采用 | 打分时按题检索 top-k chunk 注入 | 成本可控，但仍削弱分数的可解释性 |
| **C. 评价标准挂原文上下文** | ✅ **已实现，默认开启** | 打分主干不变，仍逐条判、逐条加权；在此基础上，为每条带来源的标准附上其背后**更完整的 SOP 原文段落**（按 `source_document_id`+`source_page` 从 `SopChunk` 取回并拼接，带 `max_chars` 护栏），供评委参考——不再只给一句 `source_quote` | 保住公平/可复现/可追溯，同时解决"引用太短、评委理解偏差"。原文只进 prompt 作**依据**，**不进计分引擎**（`enforce_and_score` 未改），同一组判定 ⇒ 同一分数 |
| **D. 原文覆盖度体检** | ✅ **已实现，评估时可勾选（默认关）** | 在打分之外，用该题原文段落比对本次评价标准，产出"SOP 中可能未被标准覆盖的要点"提示；**不进分数**，结果**追加进评估报告**展示 | 直接回应"标准会不会漏"的担忧，且分数依旧权威可辩护 |

**C 的落地要点：**
- 默认开启，无开关暴露给候选人；若日后需要快速关闭，可由 `include_source_context` 开关控制。
- Token/延迟护栏：每条标准原文段落设 `max_chars`（约 600 字），避免长 SOP 撑大上下文。

**D 的落地要点（客户交底口径）：**
- **触发位置**：候选人在"回顾你的回答"（review）屏，提交评测**前**可勾选一个开关
  「同时进行 SOP 原文覆盖度体检」，旁边有说明文案。**默认不勾选。**
- **不影响评分**：勾选与否，逐题得分与总分**完全一致**；D 只在报告里追加一个
  「SOP 原文覆盖度提示」板块，列出评价标准可能未覆盖的原文要点（含一小段原文佐证），**仅供参考**。
- **默认关 = 零额外成本**：不勾选时不产生任何额外的大模型调用，行为与之前逐字节一致。
- **稳健降级**：体检的大模型输出解析失败 / 无原文可比对时，静默返回"无提示"，绝不阻断报告生成。

> 对客户的表述：**"评分本身仍以固化的评价标准为准（保证公平、可复现、可申诉）；C 让评委在判每条标准时看到该标准背后更完整的 SOP 原文段落（默认开启）；D 是评估时可勾选的'原文覆盖度体检'（默认关闭），用于提示标准可能遗漏的原文要点，仅追加进报告作参考、绝不影响分数。"**

## 5. 术语对照表（便于沟通）

| 术语 | 通俗解释 |
|---|---|
| SOP | 标准作业程序原文（客户提供的知识文件） |
| chunk（切块） | 把长原文切成的小片段（约 512 字），带页码，便于检索和引用 |
| RAG（检索增强） | "先检索相关原文片段，再让大模型据此生成/回答"的机制。本系统**只在编制评价标准时用**，打分时不用 |
| checklist（评价标准/量规） | 每道题的评分依据，由若干"必答/建议/禁止"条目组成，各带权重 |
| source_quote（原文引用） | 每条评价标准背后那一小段 SOP 原文，用于溯源 |
| 4 态判定 | 每条标准的判定：符合/部分符合/未符合/违规 |
| 定档 | 报告头条结论：符合预期 / 需要改进 / 不符合 |
