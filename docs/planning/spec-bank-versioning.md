# 设计：题库版本（一套题目 + 一套评分标准 = 一个版本）

取代 [`spec-rubric-versioning.md`](spec-rubric-versioning.md)（v0.52.0.0，只给评分标准做了版本）。
2026-10-08 负责人要求，原话：

- "题目和评分标准保持一个版本"；"一套题目，一套评分标准，变成一个整体。"
- "修改了题目，或者修改评分标准，或者两者修改了，就使用一个新的版本。"
- "任何一个时刻的 snapshot 应该都是完整的合理。"
- "用户只要选择了题库和对应的版本，那么评分标准就固定下来了。"

## 为什么要改 v0.52.0.0

v0.52.0.0 只冻结了评分标准，题目仍然只有一份、原地修改。这样题目和评分标准会各自变化：

- **改题目文字**：已经进行过的面试回看时显示的是新文字，评分却仍按旧的评分标准。
- **删题、重新导入题库**：版本里按题目 ID 记录的评分条目对不上题库现在的题目，必须额外打补丁
  （v0.52.0.0 里的"导入时把用户改指到新版本"），否则整场面试都找不到评分标准。
- **AI 逐题生成评分标准**会生成只包含部分题目的中间版本，违反"每个快照都完整"。

把题目和评分标准冻结成同一个版本后，这三个问题都从根上消失。

## 版本里存什么

一个版本就是这个题库在某一时刻的**完整内容**，按出题顺序排列：

```json
{"questions": [
  {"id": "<题目 ID>", "text": "...", "language": "en-US", "order_index": 0, "enabled": true,
   "weight": 1, "expected_points": [...], "max_follow_ups": 0, "follow_up_prompt": "",
   "rubric": [
     {"id": "...", "kind": "required", "text": "...", "weight": 25, "advisory": false,
      "source_quote": "...", "source_document_id": "...", "source_page": "4.2", "order_index": 0}
   ]}
]}
```

- 题目保留**原来的题目 ID**：面试记录（`interview_turns.question_id`）按题目 ID 关联答案，
  冻结的版本必须用同一个 ID 才能把答案对回到题目上。
- `enabled = false` 的题目也存进版本里，面试只出 `enabled` 的题目。这样"禁用一道题"本身也是一次
  修改，会生成新版本。
- 评分标准就是每道题当时默认的那份 checklist（和 v0.52.0.0 一样）。

## 什么时候生成新版本

**规则：题目或评分标准有任何变化，就生成新版本；内容没变（哈希相同）就不生成。**

版本只在**完成了一次完整操作之后**生成，所以每个版本都是完整的：

| 操作 | 生成版本 |
|---|---|
| 后台新增、修改、删除、禁用、重新排序题目 | 操作完成后生成一个 |
| 后台保存评分标准、点击 AI 生成评分标准 | 操作完成后生成一个 |
| bundle 导入 / 同步脚本 | 全部题目写完后只生成一个 |
| 分配题库、开始面试 | 如果当前内容比最新版本新（有改动没有生成版本），先补一个，`reason=sync` |

**生成版本这一步放在后台接口层（admin 路由），不放在底层写入函数里。** 启动时的种子数据、私有的客户
导入脚本都是直接调用底层函数，逐题写入，中途不应该生成版本。它们写完以后，第一次分配或开始面试时，
会按当时完整的内容补一个 `sync` 版本。这样不用改私有脚本，也不会再出现只包含部分题目的版本。

## 面试怎么用版本

开始面试时固定一个版本（字段 `interview_sessions.bank_version_id`），之后这场面试的**所有**读取都只用
这个版本：

- 出题、当前题、下一题、中断后恢复、交卷前回看（`resolve_questions`，现在 7 处调用都改为读版本）
- 评分、SOP 覆盖率检查、judge、报告里 SOP 链接的权限检查（v0.52.0.0 已经这样做，改为读同一份内容）

v0.52.0.0 之前开始的面试没有版本，保持原来的行为：读题库当前的题目和评分标准。

**分配**：给用户选题库时，默认选这个题库的当前版本；管理员也可以选其他版本。选定之后就固定下来
（负责人此前已确认），之后修改题目或评分标准，只会生成新版本，不会改动这个用户的分配。

## 重新导入题库

导入会把题目换成新的题目 ID，生成一个新版本。**旧版本保持完整**：里面有旧题目的文字和评分标准，固定在
旧版本上的用户和面试，仍然按旧版本出题、评分，内容自洽，不会出现对不上的情况。

所以 v0.52.0.0 里"导入时把用户改指到新版本"的补丁，在新设计下不再是修正错误所必需的，而是一个**策略
选择**；负责人选择保持旧版本，见下面的决定 1。

## 数据迁移

v0.52.0.0 刚上线，线上 5 个题库各只有一个 v1（`initial`），没有被分配的用户。迁移做三件事：

1. 表和字段改名：`rubric_versions` → `bank_versions`；`rubric_version_id` → `bank_version_id`；
   `assigned_rubric_version_id` → `assigned_bank_version_id`。
2. 把已有版本的内容按新格式重新生成（加上题目）。线上只有 v1，且生成之后没有任何修改，所以按当前内容
   重建等价于 v1 当时的内容。
3. 已经固定在 v1 上的面试不需要改动，它们的版本 ID 不变。

## 界面

- 用户页：版本选择框文案从"评分标准版本"改为"题库版本"。
- 题库页：显示当前版本号，提示"每次修改题目或评分标准都会生成新版本"。
- 面试结果：显示"题库 v3"。
- 面试回看和报告：题目文字来自固定的版本，不受之后修改的影响。

## 负责人决定（2026-10-08）

1. **重新导入题库后，已分配的用户保持固定在原来的版本**，和"选定之后就固定"一致。旧版本自带当时的题目和
   评分标准，可以继续使用；要让某个用户用新内容，在用户页把版本改成新的。因此去掉 v0.52.0.0 里
   "导入时把用户改指到新版本"的逻辑，开始面试时的"版本和题库题目对不上就改用当前版本"的检查也随之去掉
   （新设计下面试读的是版本自己的题目，不存在对不上）。
2. **版本列表先不显示变更说明**，只显示版本号、时间和生成原因（编辑 / 导入 / 同步）。
