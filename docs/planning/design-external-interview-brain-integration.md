## Problem Statement

Phase 1 (built-in question bank + our F4 scoring + digital-human voice) passed client acceptance.
Phase 2 requirement: the client's **own interview brain** — a workflow they host behind their public
gateway — must be able to drive the interview instead of our bank, while our system provides the
digital human + voice shell. Both modes coexist; each interviewer persona picks exactly one.

The delivered contract (live-tested E2E on 2026-09-04, three-round start→message→end verified):

- `POST {gateway}/api/portal/open/difyAgent/runWorkflow/streaming`, `Authorization: Bearer <app-key>`
- Body: `{"inputs": "<hex>", "user": "<id>"}` where hex = UTF-8 bytes of the JSON
  `{event: start|message|end, conversation_id, user_input, session_state_json}` hex-encoded
- Response: **SSE stream**; the authoritative payload is the `workflow_finished` event →
  `data.outputs = {conversation_id, public_response_json, final_session_state_json,
  session_complete, speech_word_count}`
- `public_response_json` carries `speech_text` (avatar speaks), `display_text` (screen shows;
  contains internal ids like `RFCMS-Q05` that MUST be scrubbed), plus analysis/scores/radar/
  citations fields we do not consume in v1
- **The API is stateless.** Empirically proven (2026-09-04 control experiment): sending
  `conversation_id` with an empty `session_state_json` resets the interview to question 1 and
  discards the candidate's answer. `conversation_id` is an echo label, not a server-side state key.
  The caller MUST persist and round-trip `session_state_json` verbatim every turn.
- **Field-name bridge (implementer note):** the blob arrives in the response as
  `workflow_finished.data.outputs.final_session_state_json` and goes back in the next request's
  inner JSON as `session_state_json` — same bytes, different field name on each leg. One value,
  one column, two wire names.

Vendor-neutral rule (owner directive): the implementation never names the vendor. Code, tables,
config keys, and UI copy say "external interview API/server"; the concrete workflow product behind
the client's gateway is background detail only.

## Status Quo

Today one brain exists: `backend/app/interview/state_machine.py` reads the default question bank
(`resolve_questions`), decides follow-ups, completion, and triggers F4 scoring. The client's brain
is a parallel implementation of the same interview (their state carries the same RFCMS question
ids and six-dimension rubric). Without this integration the client cannot exercise their own
question flow through our digital human — the phase-2 deliverable does not exist.

## Constraints

1. **§14 division of labor (client-confirmed, restated by owner this session):** external mode =
   we speak + display + end on the completion signal; evaluation and results belong to the client
   side. On `session_complete=true` we show "interview ended" and stop — no local scoring, no F8
   report mapping in v1.
2. **Rubric-leak boundary:** `final_session_state_json` contains live per-question scores and the
   rubric. It is persisted backend-only, echoed verbatim to the API, and must never reach the
   browser or any LLM context. `public_response_json` is the only thing that crosses to the client
   UI, after scrubbing.
3. **Not an agent tool:** the external server is never attached to the Foundry agent's tools
   (client-explicit). Our backend calls the API in code, in a controlled sequence.
4. **Vendor-neutral naming** in all code/config/UI (owner-explicit this session).
5. **Zero regression to phase-1:** the shipped bank mode must be untouched — it just passed
   acceptance.
6. **Voice transport unchanged:** `useInterviewVoice.ts` `speakQuestion(text)` /
   `commitAnswer()` remain the only voice seam. Orchestration (page-level awaiting/failure/resume
   states) is where new frontend work lands.
7. **Secrets:** the delivered app-key circulated in plaintext (chat/docs) and is a **test key
   only** — it must never be used in production. The production key is entered by the admin in the
   admin config UI (owner decision 2026-09-04); no rotation handoff from the client is required.
   Keys live only in Fernet-encrypted config
   (existing `ServiceConfig` pattern), masked in admin UI with click-to-reveal (owner-requested),
   boot-seedable from env (v0.35.0.0 pattern). Masking reuses the existing `mask_key()` convention
   (`config_service.py:59`): star the prefix, show the **last 4** chars (e.g. `****g4IL`).
   The reveal endpoint is a deliberate relaxation of the existing "API key is write-only"
   invariant (`admin_config.py`), owner-confirmed 2026-09-04 (kept over the reviewer's
   write-only recommendation). It is scoped as a **bounded exception**: only the
   `external_interviewer` key is revealable; the AI-Foundry key stays write-only. Eng-review
   ground truth (2026-09-04): the codebase has **no audit-log and no rate-limit helper** — both
   `mask_key`-style reveal safeguards would be net-new. Feasible safeguard tier:
   **MUST** — admin-JWT only (reuse the existing admin dependency), plaintext returned **only**
   by an explicit dedicated reveal route (never by the default GET, which still returns the mask),
   and the plaintext is **never written to any log**; **SHOULD** — a one-line reveal audit record
   and a per-admin rate limit, both small net-new helpers, deferred if they slip the slice.
8. Default interview language is en-US app-wide (v0.36.0.0); the external API is English-only for
   now (client-confirmed 2026-08-25) — no new i18n mapping for its content, UI chrome stays
   bilingual.

## Premises (all confirmed by owner 2026-09-04, amended by live experiment)

1. Two modes, chosen per persona, never mixed. v1 external mode renders no local report; on the
   completion signal the UI marks the interview ended ("等到进一步的联系" — further contact is a
   client-side concern).
2. Because the API is stateless, **we** persist `conversation_id` + the opaque state blob on
   `InterviewSession` and round-trip it each turn. (Owner initially challenged this —
   "记住 conversation_id 不就可以了吗?" — settled by the reset experiment above.) Blob is
   backend-only per Constraint 2. Bonus: persistence enables disconnect/refresh resume through the
   existing `find_resumable_interview` lookup — which is why the design keeps external sessions'
   top-level `status` inside that function's existing filter (see Lifecycle/status below) rather
   than inventing a new top-level status it would not match.
3. Integration shape: a **parallel runner** beside the state machine (Approach B below), plus an
   admin per-persona brain selector and an external-API connection config. Never via ToolPicker.
4. Both outputs are used: `speech_text` → `speakQuestion()`; scrubbed `display_text` → the
   existing on-screen question area (they differ: speech carries the preamble + ordinal, display
   carries the id + title — confirmed live).
5. This connection config ships as the seeded default config now (owner: "现在就作为默认的配置"),
   with masked key display.

## Cross-Model Perspective (Codex cold read, 2026-09-04)

- **Steelman:** a durable per-persona adapter where the product becomes "a resumable,
  failure-aware voice shell" that securely round-trips opaque client state and exposes only
  candidate-safe content.
- **Center of gravity (quoted):** *"The API is STATELESS: caller must round-trip
  session_state_json verbatim each turn"* — we are taking responsibility for continuity,
  concurrency control, crash recovery, and exactly-once turn advancement; get it wrong and an
  interview silently forks, repeats a question, or attaches an answer to the wrong turn.
- **Challenged premise:** "voice layer untouched." Verdict after cross-check: transport truly is
  untouched (the seam is a plain string), but the **conversation orchestration layer** cannot be —
  it needs awaiting-external, retryable-failure, ambiguous-timeout, and resume/replay semantics.
  Premise amended accordingly (Constraint 6).
- **Hardening list adopted into Approach B:** commit-before-speech; per-session turn
  serialization (optimistic lock / CAS); pending-answer dedup; replay-last-committed-response on
  reconnect (never re-call the API for a replay); bounded auto-retry of ambiguous timeouts (safe here
  because the API is stateless and a retry re-sends the last committed state — see Failure protocol,
  amended from Codex's original "never auto-retry" per owner's idempotent-assumption decision);
  `recovery_required` sub-state with a fixed local avatar failure line + 恢复 only after retries exhaust;
  SSE robustness (chunk boundaries, keepalives, size limits, deadlines, only `workflow_finished`
  is authoritative); fake external server test suite.

## Approaches Considered

### Approach A: Minimal vertical slice
Independent runner, happy path only; env-only config; generic error on failure.
Effort S-M · Risk Medium · Completeness 4/10.
Rejected: a live client demo dies on the first network hiccup; no admin key management
(violates Premise 5); recovery retrofit costs more later.

### Approach B: Parallel runner + production hardening (CHOSEN)
New `external` brain path beside the untouched state machine, carrying the Codex hardening list
(phased: core invariants now, latency/idempotency-dependent parts gated on client answers),
complete admin surface, and a fake-server test suite.
Effort M-L — with two honestly-sized novel pieces: the CAS turn lock has **no precedent in this
codebase** (kept to one single-statement UPDATE...WHERE pattern to bound the risk), and the
`InterviewPage.tsx` phase work is a real branch point (6 existing phases across two layout
families), not a fold-in. Risk Low · Completeness 9/10.

### Approach C: Generic InterviewSource seam inside state_machine (original spec §11 sketch)
Protocol + registry threaded through `resolve_questions`/`answer_finalized`.
Effort M-L · Risk Medium-High · Completeness 7/10.
Rejected: modifies the just-accepted phase-1 core; the external mode uses none of the state
machine's logic (ordering/follow-ups/scoring all live on the other side), so the seam contorts an
all-questions-at-once interface around a turn-by-turn brain — paying today for a hypothetical
second external brain.

## Recommended Approach (B) — architecture

**Naming (vendor-neutral):** `external` is the mode name everywhere.

Backend:
- `backend/app/services/external_interview_client.py` — transport client: builds the inner JSON
  `{event, conversation_id, user_input, session_state_json}`, hex-encodes exact UTF-8 bytes,
  POSTs, parses SSE defensively (tolerate chunk splits/keepalives/unknown events; authoritative =
  `workflow_finished.data.outputs`; enforce content-type, response-size cap, connect/read/total
  deadlines). Returns a typed `ExternalTurn{conversation_id, state_blob, speech_text,
  display_text, session_complete}`. The state blob is validated for presence, never parsed.
  Registry + `mock` implementation for CI, imitating `voice_providers.py`.
  **Transport (eng-review ground truth):** `httpx>=0.27` is already a base dep and the whole
  backend is async — reuse the established short-lived `async with httpx.AsyncClient(timeout=…)`
  pattern (`voice_providers.py:130`, `admin_config.py:141`) with `except httpx.HTTPError` fail-soft.
  No SSE library exists yet: add `httpx-sse`, or hand-roll a line parser over
  `client.stream("POST", …)`. Crucially, **this is server-to-server SSE consumed to completion**
  (we wait for `workflow_finished`, commit, then return) — the external answer route is a **normal
  async JSON handler on `get_db`** returning `InterviewOut`, **not** a browser `StreamingResponse`,
  so the `get_session_factory` streaming-session dance (`db.py:39`) is not needed.
- `backend/app/interview/external_runner.py` — orchestration: start/answer/end turns; per-session
  serialization via an optimistic-lock version column: `UPDATE interview_sessions SET ... ,
  turn_version = turn_version + 1 WHERE id = :id AND turn_version = :seen` with a rowcount check —
  a lost race returns HTTP 409 to the late request. **This is a new pattern for this codebase**
  (no CAS/version-lock precedent exists — verified), so it is deliberately kept to this one
  single-statement shape; no generic locking framework. **Eng-review note (2026-09-04):** the
  reviewer first floated SQLAlchemy's built-in `version_id_col` optimistic lock and then withdrew
  it after reading the code — the built-in guards only "did this row change," not the *business*
  guard `external_phase != 'awaiting'`, and it works at ORM-flush level (a read-modify-write
  window). The single atomic `UPDATE … WHERE turn_version=:seen AND external_phase!='awaiting'` is
  the correct primitive here and is kept. One durability caveat on the deployment's `aiosqlite`
  backend: concurrent writers can surface `database is locked`, so the runner sets a short
  `PRAGMA busy_timeout` (or retries the CAS UPDATE briefly) rather than letting a lock error 500. **The version bump happens at submit, not
  at commit:** accepting an answer first CAS-reserves the turn (`... external_phase='awaiting',
  turn_version = turn_version + 1 WHERE id = :id AND turn_version = :seen AND external_phase !=
  'awaiting'`); only the winner proceeds to call the stateless external brain. A second *distinct*
  answer arriving during the awaiting window fails that reservation and gets 409 **before any
  external call is made** — so two different answers can never both hit the client's brain for the
  same turn. (Identical resubmits are short-circuited earlier by the pending-answer hash, returning
  the in-flight/last response rather than a 409.) The later commit is a second guarded UPDATE
  keyed on the reserved version, so a stale commit also cannot land. **Commit-before-speech**:
  atomically persist new state blob + last committed public response, then release `speech_text`
  to the client. Failure protocol (owner decision 2026-09-04 — proceed on the idempotent
  assumption): a turn auto-retries, **bounded (2 attempts)**, by re-sending the **same pending
  answer + the previous committed state** under the lock. This is safe precisely because the API
  is stateless and we own the state — each call is a pure function `f(state, answer)`, so a retry
  cannot fork or double-advance; a non-deterministic LLM at worst returns a different-but-valid
  single next question. Pre-acceptance failures (connect errors, 5xx before any SSE frame) retry
  the same way. **Only after retries exhaust** does the session enter `recovery_required`: the
  avatar speaks one fixed local failure line and the candidate sees a single **恢复 (Recover)**
  action — re-send under the lock; if no answer is pending, it silently re-renders the last
  committed response (no API call). `display_text` scrub: strip the internal id prefix
  (`RFCMS-Qxx —`) → ordinal "Question N" form.
- Lifecycle/status: the top-level `InterviewSession.status` stays within its existing values
  (`in_progress` throughout, `completed` on `session_complete`) so
  `find_resumable_interview` (`state_machine.py:46`, filters `status == "in_progress"`) resumes
  external sessions **unmodified**. The external sub-state lives in a new nullable column
  `external_phase: "idle"|"awaiting"|"recovery_required"|None` — recovery is a sub-state of
  `in_progress`, not a new top-level status. **Resume must branch on `external_phase`:** a refresh
  while `external_phase == "recovery_required"` re-renders the recovery prompt (the 恢复 action is
  still owed and must stay visible), *not* the silent last-response replay used for the healthy
  `idle` case. A refresh while `awaiting` also lands on `recovery_required`-style handling: the
  in-flight turn's outcome is unknown to a fresh page, so it presents the recovery prompt rather
  than assuming the last committed response is current.
  **Durability boundary (eng-review, owner-accepted 2026-09-04):** all external state
  (`external_state`, `external_conversation_id`, `external_last_response`, `turn_version`) lives in
  the deployment's **ephemeral SQLite**, which `entrypoint.sh` reseeds every boot. So the
  commit-before-speech / resume hardening protects **within one container lifetime only** — network
  blips, tab refresh, duplicate/concurrent submits. A container **restart or redeploy abandons any
  in-progress external interview** (the row is gone with the DB), exactly as it abandons an
  in-progress bank-mode interview today. This is accepted, not fixed: interviews run minutes,
  restarts are rare, and adding a durable store would diverge from the shipped ephemeral-SQLite
  architecture. Resume claims below (Success Criteria 2) are scoped to within-lifetime accordingly.
- `backend/app/api/interview.py` — route by the session's **snapshotted** brain mode at the three
  touchpoints (start / answer / current-question); reuse `AnonymousCandidateSession` auth.
  `InterviewTurn` rows keep being written so the transcript works unchanged, with exactly this
  content: interviewer turns store the **scrubbed `display_text`**, candidate turns store the same
  transcript text sent as `user_input`; the state blob never enters a turn row. Report endpoints
  return "external mode — results are managed by the interview provider" for external sessions.
- Models: `InterviewSession` + `brain_mode: "bank"|"external"` (**a per-session snapshot copied
  verbatim from `InterviewerPersona.interview_brain` at start**, so flipping a persona's brain
  later never re-interprets past sessions — the two columns hold the same enum and are meant to
  mirror; the persona is the source of truth, the session is the frozen copy),
  `external_conversation_id: str|None`, `external_state: Text|None`,
  `external_last_response: Text|None` (the full scrubbed `public_response_json` used for replay —
  resume re-renders its text silently and does **not** re-trigger `speakQuestion()`),
  `external_phase` (above), `turn_version: int default 0`. `InterviewerPersona` +
  `interview_brain: "bank"|"external"` (default `bank`). Alembic migration, nullable columns
  only — zero impact on bank mode.
- Config: `ServiceConfig` row `service_name="external_interviewer"` — endpoint URL, Fernet-encrypted
  api key, and a **user-tag prefix**: a static per-deployment string (e.g. `aiinterview-prod`)
  prepended to the anonymized session id to form the gateway `user` field, so the client can
  attribute traffic per environment. Boot-seed from env (`EXTERNAL_INTERVIEWER_ENDPOINT` /
  `EXTERNAL_INTERVIEWER_API_KEY`) mirroring the v0.35.0.0 master-config seeding; admin GET returns
  the key masked per `mask_key()` (`****g4IL`); reveal endpoint per Constraint 7.

Frontend:
- Persona editor: "面试大脑 / Interview brain" selector (内置题库 built-in bank | 外部面试 API
  external interview API), bilingual copy.
- Admin config section: endpoint + masked key with click-to-reveal + test-connection button.
  The probe sends a single `event:"start"` call with the reserved user tag
  `{user-tag prefix}-healthcheck`, renders the returned `speech_text` as proof, and creates **no**
  `InterviewSession`/`InterviewTurn` rows. No cleanup call is needed — the API is stateless, so
  nothing exists server-side to clean up (the client can filter the `-healthcheck` tag out of
  their analytics).
- `InterviewPage.tsx`: the new states extend the existing `Phase` union and **inherit the live
  stage layout** (avatar remains on screen; awaiting/recovery render as overlays on the stage, the
  same layout family as the in-interview phases — not the centered pre-interview column).
  Completion on `session_complete` uses the existing completed-phase layout with external copy
  (zh-CN "本场面试已结束,结果将由主办方另行联系" / en-US "This interview has ended; the organizer
  will follow up with you separately"). **Mic policy during awaiting-external:** capture is
  paused the moment an answer is committed and stays paused until `speakQuestion()` for the next
  turn completes; any utterance in that window is intentionally discarded (not buffered) — the
  awaiting indicator (zh-CN "面试官思考中…" / en-US "Interviewer is thinking…") tells the candidate
  they are not being heard. All chrome strings ship as bilingual i18n keys per Constraint 8
  (en-US default); the Chinese/English pairs shown here are the drafted copy, not placeholders. This reuses
  the existing commit-then-speak gating; external mode only lengthens the window (network+LLM
  seconds vs local ms). Resume path renders `external_last_response` text without re-calling the
  API and without re-speaking.
- Voice transport: `speech_text` feeds the existing `speakQuestion()`; nothing else changes.

Abandonment policy: if a candidate closes the tab or the anonymous session expires mid-interview,
we do **not** send `event:"end"` — the API is stateless (empirically verified), so there is no
server-side session to leak or clean; the row stays `in_progress` indefinitely, exactly as an
abandoned bank-mode session does today (there is **no** background status-expiry sweep in the
codebase — only the anonymous-token TTL, which gates resume access but never mutates
`interview_sessions.status`). If unbounded `in_progress` growth ever matters it is a pre-existing
bank-mode concern to solve once for both modes, out of scope here. `event:"end"` is sent only on an
explicit in-UI exit action.

Testing (two slices — hardening is gated on facts, not built ahead of them):
- **Slice 1 (build now):** fake external server (FastAPI fixture) replaying the three recorded
  live rounds from 2026-09-04 as golden files (start/message/end), plus: fragmented SSE frames,
  malformed hex/JSON, missing `workflow_finished`, expired key (401), duplicate submit, and two
  concurrent answers (CAS 409). Commit-before-speech verified by a fault-injection hook in the
  runner (an injectable raise between state-commit and response-delivery — no real process kill),
  asserting the committed state survives and resume replays it.
- **Slice 2 (tuning, after a first live run against the real workflow):** delayed-stream/timeout
  matrix tuned to the observed p95 latency (a generous default timeout — e.g. 60s — holds until
  measured); the auto-retry bound validated against the real workflow; defensive handling of any
  event beyond `main_question`/`session_complete` (incl. an `error` payload) exercised.
- Regression: full existing bank-mode test suite must stay green untouched; assert no browser
  payload ever contains `final_session_state_json` (response-shape test on every candidate
  endpoint).

## Decisions (owner, 2026-09-04 — resolved internally; no client message required)

The four questions once owed to the client were all settled by the owner without needing to ask:

1. **Key rotation → not a client ask.** The circulated app-key is a **test** key; the production
   key is entered by the admin in the admin config UI. Standing constraint: never promote the test
   key to prod. (Constraint 7.)
2. **Idempotency → proceed on the idempotent assumption.** Bounded auto-retry is safe because the
   API is stateless and we retry from the last committed state (see Failure protocol) — no
   dependency on a gateway idempotency key.
3. **Real-workflow latency → don't block on it.** Set a generous default timeout (e.g. 60s) and
   tune from the first live run's observed p95 (Slice 2). Not a client question.
4. **Event enumeration → not needed.** We consume only "next question" + `session_complete`, plus a
   defensive check for an `error` payload; every other event is ignored by design.

Deferred (product, phase-3 — not now): the API also returns analysis/scores/radar through us;
whether to render them in our report page later, or keep results exclusively client-side, is a
phase-3 decision. v1 = client-side only, per §14.

## Success Criteria

1. A persona set to `external` runs a full live interview through the digital human: avatar speaks
   `speech_text`, screen shows scrubbed `display_text`, candidate answers by voice, turns advance,
   `session_complete` ends with the closing UI state. Verified against the client gateway.
2. Refresh/disconnect mid-interview resumes at the same turn, replaying the last committed
   response, without an extra API call and without the state blob ever appearing in any browser
   payload (assert in tests).
3. Duplicate/concurrent submissions cannot fork the state (CAS test passes); chaos suite green.
4. Existing bank mode: entire pre-existing test suite green with zero diffs to
   `state_machine.py`.
5. Admin: brain selector + connection config with masked key/click-to-reveal work; key stored
   Fernet-encrypted; boot-seed from env verified on a fresh deploy.
6. `ruff format` + CI green (project rule).
