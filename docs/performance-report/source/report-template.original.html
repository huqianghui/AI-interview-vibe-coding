恢复的失败点在 Azure 之前

后端先接受 WS，再校验应用 token。AUTH_FAILED 由后端发出并关闭连接；这三次不会创建新的 Voice Live 会话。时间间隔与后台重连的剩余 2 / 4 秒 backoff 相符。

部署版本代码中，首次连接的鉴权失败会终止；但后台 reconnect 的 pre-live error 路径没有把鉴权错误单独归类，因此可能耗尽剩余预算后才显示通用连接失败。

有依据，仍需限定

缓存凭据过期与记录高度吻合

同一 operation 在 16:11:57 创建过匿名 session；到 20:00:16 恢复已过约 228 分钟，代码默认有效期为 120 分钟。WS 重连只重新读取缓存 token，导出记录中未见中途再次创建 session。

实际 exp、当时有效 TTL 与撤销原因没有导出，不能排除撤销或签名变化。也不能由 1006 推断原始断开就是 token 过期、网络故障或 Azure 故障。

优化应同时处理错误分类与面试归属。 对 AUTH_FAILED 停止无效重试、展示具体恢复入口是直接线索；“刷新 token 就无损续接”尚不成立，因为旧面试绑定原匿名 session ID，新建 session 不自动接管它。需要设计保留原面试所有权的续期/恢复策略。

原 WS 的开始时间使用墙钟，duration 使用 performance.now；没有独立 closed_at。开始时间加 duration 得到的结束点是推算值。中间长时间空档是否与休眠/挂起有关，现有数据无法还原。异常时段 16:10–20:05 未查到前后端平台事件，语音样本时段 RestartCount 为 0；这仍不足以确定 1006 的根因。

06 / MEDIA IS ITS OWN PATH媒体大体稳定，缓冲比丢包更值得关注

73 个媒体窗口均为 512×512、约 25 fps。记录中的包丢失很低，但音频 jitter buffer 的窗口平均等待最高达到 431 ms。低丢包不自动等于低播放延迟。

不要让最长的会话代表所有用户。 66 / 73 个窗口来自一场长会话，占 90.4%。因此报告逐场展示分布，不用一个总体平均掩盖另一场约 409 ms RTT、123 ms 缓冲的情况。
1 kbps 音频不代表带宽不足。 长会话的多数窗口音频接收约 1 kbps，视频仍约 500 kbps。低音频码率可能对应静音或静音抑制；遥测没有逐窗讲话状态，具体原因未确认。要结合讲话状态、帧率和包数理解，不能单看接收码率下结论。

RTT 与 audio jitter 是每个窗口末尾读数；丢包率、码率和帧率由计数器增量计算；jitter buffer 是窗口内平均排队时间。它们不是窗口最高值，也不是所有用户的独立样本。未上报每条连接的音频 codec，不在报告里把它假定为已验证的 Opus。

08 / SCORING IS NOT A SINGLE BLOCK46 秒与 70 秒，究竟在等待什么？

两条报告记录都包含 9 个逐题评分任务。模型 HTTP 真正开始的时间，比“评分任务已开始”更晚；较慢的一条还增加了一轮附加业务调用。下面使用当时的历史代码对应路径，不以 README 的旧测量替代实际结果。

三组调用都出现的形状

8 个 HTTP 先开始，第 9 个贴着已有请求结束点才开始。 首份报告的最后一个评分任务在 HTTP 开始前等待了 20.293 秒；HTTP 本身耗时 25.791 秒。业务 span 与 HTTP span 之间的差，不能直接叫模型推理。

优化假设

历史代码没有 Semaphore(8)，9 个评分 span 也同时开始，排除了“第 9 个任务卡在外层评分信号量”的解释。同步 Responses SDK 使用 asyncio.to_thread；默认执行器或 SDK 发起前资源队列是强候选，实际历史线程池容量尚未取得。

为什么第二轮判为 SOP coverage 附加审计

评分结束后，9 个新的 Responses HTTP 直接挂在报告请求下，没有 scoring.question 父 span。历史代码只有开启 sop_coverage_check 后，才会在此位置并发执行每题 coverage 审计；该路径当时没有专属业务 span。开始顺序、数量和父子关系均吻合。

高置信源码归因 请求选项没有写入遥测，报告未读取候选人报告正文来确认。第二轮约 46.836 秒，占 70.417 秒请求的约 66.5%。这属于额外工作量，不能据此判定 NDJSON 比普通 HTTP 慢。

时间窗对应版本：第一条 574f390 / revision 0000137；第二条 5738027 / revision 0000139。映射来自 revision 创建时间窗，未取得 trace 内显式 revision 标签；两版本相关评分/coverage/适配器代码一致。

10 / WHAT TO IMPROVE NEXT按证据强度和用户收益排优先级

这些是分析建议，尚未实施或验证收益。已经存在的二进制上行、ICE 提前发送、首读预热、播放缓冲、评分并发、Nginx 无缓冲，都不再作为“新增优化”重复推荐。

P1 · 恢复正确性 直接证据

鉴权失败从网络重试中分离

一次链路里 3 次 AUTH_FAILED 占据 17.428 秒恢复窗口，均未到 Azure。先处理不可重试错误分类、准确提示和原面试归属的续期恢复。

预期改善
减少不可成功的建连等待；避免把鉴权问题显示成普通网络连接失败。
验证方式
覆盖过期/撤销、后台重连与保留原面试恢复；分别统计首失败到明确提示、实际恢复成功率。
P1 · 评分尾延迟 强线索

检查同步 SDK 发起前的队列

三组调用都出现 8+1 出站形状；最慢任务在 HTTP 开始前已等待 20.293 秒。同步 responses.create 经 asyncio.to_thread 执行，是优先核查位置。

预期改善
压缩等待最久任务的前置排队；不承诺消除全部 20 秒，也不把增加 semaphore 当成答案。
验证方式
核对实际 executor 容量、线程提交到运行时延；评估原生异步客户端或明确执行器配置，再按同题数、同模型与配额比较。
P2 · 语音响应 关键路径已分解

优先削减往返与起音等待

7 对精确匹配的正式回答请求中，server 中位数 56 ms，后端计时之外中位数 263 ms；随后 read 接受中位数 259 ms，created→起音 631 ms。优化应落在这些段，而不是假定读题仍等待文本推理。

可评估方向
受控对比客户端接入路径；评估提交事务完成后协调读题，减少顺序往返；保留明确提交、去重及事务一致性。
验证方式
同一协议、相同问题文本、同网络下比较每回合阶段。read→created 还含 Azure 受理，不全是可消除的网络时间。
P2 · 报告体验 高置信业务归因

让附加审计成为单独可理解的阶段

70.417 秒例子中，评分完成之后的额外模型工作约占 66.5%。界面与性能报告应明确“评分完成、coverage 仍处理中”，并评估先呈现评分后继续附加审计的产品取舍。

验证方式
同工作量对比 coverage 开关；单独统计 grading、coverage、最终报告完成，确认最终结果完整性。
注意
代码已有 coverage 进度及心跳；本建议侧重阶段表达与是否延后附加工作，不把现有机制当缺失。
P2 · 数字人准备 4 次握手

关注媒体路径与 ICE 后的等待

ICE gate 仅 476–678 ms，已有可用候选后提前送 offer；ICE connected→首帧仍有 1.019–1.390 秒，包含 DTLS完成、媒体到达与首帧检测。

验证方式
按相同终端、出口网络、relay 路径对照；结合音频缓冲，区分建立耗时和起音等待。当前没有 TCP/TLS relay 的比较证据。
P3 · 规模化准备 架构条件

先预算状态与数据库，再扩副本

当前语音样本资源余量充分。若增加并发，需要先盘点进程内防重、长连接生命周期、录音缓冲、评分总并发和 DB 连接预算。

验证方式
在授权的独立负载验证中测并发阶梯；记录排队、TTFA、连接数、credits 与失败原因。现有轻负载数据不给出虚构的并发容量数字。
