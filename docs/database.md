# 数据库：PostgreSQL 与数据持久化

线上部署的所有数据都存在 **Azure Database for PostgreSQL** 里，包括面试官、题库与评分标准、SOP 文档、用户和分配、每一次面试记录和报告、配置等。本地开发和测试默认仍然用 SQLite。

本文说明三件事：数据库怎么部署、怎么连接、哪些行为是为「数据会一直保留」专门设计的；最后一节是切换到 PostgreSQL 后做的并发排查。

## 一、为什么换成 PostgreSQL

这次之前，后端用的是**容器里的一个 SQLite 文件**（`./data/ai_interview.db`），没有挂载持久卷。

- **问题：** 每次发布或重启，容器都从一个空数据库开始，只重新写入启动初始化的默认数据。管理员建的面试官、给用户做的分配、所有面试记录和报告，下一次发布就全没了。
- **结果：** 2026-10-07 线上就丢过两个手动建的面试官。
- **为什么以前能忍、现在不行：** 以前库里多半是启动时自动写入的数据（默认题库、默认配置），丢了下次启动会重新写入。v0.49.0.0 之后，库里开始存**用户自己产生、无法重建的数据**：管理员建的面试官、用户分配、每场面试的记录和报告。这些丢了就找不回来，所以必须持久化。
- **换库不改功能：** 应用通过 SQLAlchemy 访问数据库，两种库共用同一套代码，业务逻辑不变，本地开发和测试仍然用 SQLite。换库只是为了让数据在发布和重启后保留下来。

| 项目 | 取值 |

| 成本（公开价，瑞典中部） | 计算约 $14.5/月（$0.0199/小时），存储 $0.1369/GB/月，32 GB 约 $4.4/月；备份存储另计 |

## 三、应用怎么连接

连接设置由后端两个环境变量决定：

```
DATABASE_URL  = postgresql+asyncpg://id-aiinterview-public-backend@psql-aiinterview-public.postgres.database.azure.com:5432/ai_interview
DATABASE_AUTH = entra
```

- **URL 里没有密码：** 用户名就是托管身份的名字。
- **`DATABASE_AUTH=entra`：** 后端每建立一个新连接，都用托管身份现取一个 Entra token 当密码，并强制 TLS。实现在 `backend/app/db.py` 的 `make_engine()`，Alembic 迁移也走这里。
- **token 有效期约一小时：** 所以不能在启动时写死进 URL，只能在建连接时现取。
- **取 token 放在后台线程：** 取 token 可能要走网络，放在后台线程里取，不阻塞同时在处理语音 WebSocket 的事件循环。
- **专用的长期凭据：** 数据库用一个单独的、不会被重建的凭据对象，token 缓存得以保留，绝大多数新连接不需要再走网络。
- **连接池：** 显式设为 10 个常驻、最多再加 15 个（共 25 个）。B1ms 的 `max_connections` 是 50，其中 10 个保留，应用能用约 40 个，余量留给迁移，以及版本切换时短暂并存的第二个实例。
- **保持在线：** 连接最多复用 30 分钟就重建，复用前先探测一下是否还活着。

本地开发：不设 `DATABASE_AUTH`（默认 `password`），`DATABASE_URL` 指向 SQLite 或本地 PostgreSQL 即可。

## 四、启动时会做什么，以及为什么不会改坏已有数据

后端每次启动（`backend/entrypoint.sh` → FastAPI lifespan）依次执行下面几步，**每一步都是幂等的**。全新数据库和已有数据的数据库走的是同一套流程。

1. **`alembic upgrade head`：** 把表结构升级到最新。
   - 在 PostgreSQL 上会先拿一把 advisory lock。版本切换时新旧两个实例可能同时启动，后启动的那个会等前一个迁移完成，然后发现已经是最新版本，什么也不做。
2. **导入客户题库包：** 从私有 blob 下载题库包并导入 rf-CSM 题库。已经存在的题库会跳过。
3. **导入内置题库和客户附加题库：** **只创建还不存在的**，同名的题库一律不替换。
   - 以前是「删掉再重建」。那时数据库每次都是空的，所以没问题；数据持久以后，每次重启都会让题库换新 ID，把所有用户的分配、每场面试记录的题库清空。v0.50.0.1 修掉了这个问题。
4. **默认题库：** 已经有默认题库就什么都不做。没有的话，优先把已存在的「Demo interview bank」设为默认，它带评分标准；都没有时才新建。
5. **账号、默认面试官、配置：** 都是「不存在才创建」。

由此带来两个使用上的变化：

- **环境变量里的配置只在第一次启动时写入：** 包括 Foundry 连接、外部面试接口、管理员账号这些。以后改环境变量不会覆盖数据库，要在管理后台里改。
- **有意更新已有题库：** 用管理后台的题库同步（见 `RUNBOOK-bank-sync.md`）。同步会原地替换题目和评分标准，**保留题库 ID**，所以分配到这个题库的用户不受影响。代价是：已经用旧题目答过的面试，题目 ID 已经不存在了；对它重新评分，会按新的评分标准来评。

## 五、数据库与 Foundry agent 的关系

面试官的完整定义存在数据库里：提示词、声音、形象、工具、挂载的知识库（`persona_knowledge_configs` 表），以及对应 Foundry agent 的名字、版本和同步状态。

- **原件与副本：** Foundry 里的 agent 是同步时从数据库生成的副本，**数据库是原件**。
- **在 Foundry 门户里直接改 agent：** 下次在我们后台保存或重新同步时，会被数据库里的定义覆盖。所以知识库这类配置要在我们的后台里挂。

## 六、切换到 PostgreSQL 后的并发排查（2026-10-07）

SQLite 同一时刻只允许一个写操作，很多「先查再写」的代码因此从来没有真正被并发打过。PostgreSQL 默认的隔离级别是 READ COMMITTED，可以真正并发写，所以把这类代码全部排查了一遍。

**已修复：**

| 问题 | 影响 | 修法 |
|---|---|---|
| 外部面试的 `/start` 在**事务开着的情况下**等外部接口返回（含重试） | 双击或刷新时，两个请求互相看不到对方还没提交的行，建出**两场面试、两个外部会话**；同时一直占着一个连接 | 新行**先提交、再调用外部接口**（状态 `awaiting`）；加部分唯一索引 `uq_one_live_interview_per_candidate`（每个候选人会话最多一场进行中的面试），抢输的一方改为续接对方那场 |
| 题库面试的 `/start` | 同样可能产生两场进行中的面试 | 同一个索引，加冲突后续接 |
| 连接池耗尽 | 评分（每题约 18 秒）、判断、外部面试、评分标准生成都在等 LLM 或外部接口时开着事务，大约 15 个同时进行就会把整个连接池占满，连登录都会卡住 | 这些路径在调网络之前先结束事务，把连接还回池；连接池显式设为 10 + 15 |
| 版本切换时两个实例同时跑迁移 | 迁移的 DDL 互相冲突，可能导致其中一个实例启动失败 | Alembic 在 PostgreSQL 上先拿 advisory lock |
| 面试官重名 | 应用层检查是「先查再写」，两个同时创建都能通过 | 唯一索引 `uq_persona_name_ci`（忽略大小写和首尾空格），冲突返回 409 |
| 同一道题出现两个默认评分标准 | 两个同时「生成」，各自降级旧的再插入新的 | 部分唯一索引 `uq_one_default_checklist_per_question` |

对应迁移 `d8e9f0a1b2c3` 会**先清理已有的重复数据**，再建索引，所以客户环境的老数据也能顺利升级：
- **进行中面试重复：** 保留最新那场，其余标记为已放弃。
- **默认评分标准重复：** 保留最新的。
- **面试官重名：** 后来的那个自动加 「(2)」 这样的后缀。

**验证方式：**
- **SQLite：** 新增的并发测试用文件版 SQLite 和两个独立会话真实交错执行。修复前的代码上，两个 `/start` 会拿到不同的面试；修复后是同一场。
- **PostgreSQL 16：** 同样的场景在本地 PostgreSQL 16 上实测通过；两个迁移同时启动也都成功退出。

**检查过、确认没问题的：**
- **答题的乐观锁：** 带 `turn_version` 条件的 UPDATE，在 PostgreSQL 上会拿行锁，输的一方重新判断条件后匹配不到行，返回 409。外部面试的回合预留同理。
- **单默认面试官 / 单默认题库：** 两条部分唯一索引在 PostgreSQL 上都已建好，冲突返回 409。
- **一个账号只占一个登录席位：** 唯一索引兜底，冲突时复用已有的那个。
- **进程内的防重：** 判断、评分「正在进行」的进程内集合，在检查和登记之间没有 await，所以在 asyncio 里是原子的。
  - **前提：** 后端只跑一个实例（maxReplicas=1）。将来要多实例，必须先把这两处换成数据库锁。
- **语音 WebSocket：** 连接建立前就把数据库会话关掉了，代理语音期间不占数据库连接。

**已知、暂不处理：**
- **配置写入和启动初始化撞车：** 只会在启动初始化写配置的同一刻，恰好有管理员保存配置时出现。最坏结果是那次保存返回 500，重试即可，不会写坏数据。
- **候选人提交评分与管理员「生成报告」同时触发：** 会多花一次 LLM 评分费用，最后写入的那份报告生效，不会损坏数据。

## 七、数据库停机：检测与自动拉起（2026-10-08，2026-10-09 更新）

**谁在停它**：订阅级的治理自动化，每天 16:05 UTC（北京时间 00:05）停止服务器，调用者是本租户目录之外的应用身份（活动日志实测 2026-10-07、10-08）。我们无法阻止它停，只保证它被停之后几分钟内自动启动。

**现象**：线上所有登录都要等 60 秒，然后报"登录失败 (500)"，而 `/api/health` 一直返回 200。

**原因**：订阅管理员把 PostgreSQL 服务器停掉了（activity log 里是一个外部应用身份执行的 `stop`）。
当时后端连接数据库没有设超时，用的是 asyncpg 默认的 60 秒；超时后抛出的 `TimeoutError` 没有被处理，
于是变成了一个没有任何原因的 500。

**现在的处理**（v0.51.0.2 / v0.51.0.3）：

| 层 | 做什么 |
|---|---|
| 连接 | 超时 10 秒（`CONNECT_TIMEOUT_S`）；连不上抛 `DatabaseUnavailableError`，返回 **503** 并给出原因 |
| `/health` | 只看进程是否存活，**不碰数据库**，所以数据库停机不会让部署失败 |
| `/health/db` | 单独检查数据库：执行一次 `SELECT 1`（8 秒超时）。正常时返回 200 和往返耗时；失败时返回 **503** 和失败类型（只报类型，不暴露主机名） |
| **自动启动任务**（主要手段） | Azure Container Apps 定时任务 `caj-aiinterview-public-dbstart`，**每 5 分钟**由 Azure 自己的调度器运行一次 `backend/scripts/db_autostart.py`：服务器是 Stopped 就启动它并等到 Ready。用后端的托管身份，只授予自定义角色「AI Interview PostgreSQL Starter」（只能读取和启动这台服务器，不能停止或修改）。基础设施：`infra/azure/modules/db-autostart-job.bicep`；每次部署都把任务更新到最新的后端镜像 |
| `db-keepalive.yml`（备用） | GitHub 定时任务，每 10 分钟一次：服务器是 Stopped 就启动它，再通过 `/api/health/db` 端到端确认。GitHub 的定时任务不保证准时（实测曾 12 小时以上没有运行），所以只作备用 |
| `deploy-app.yml` | 部署完成后检查一次 `/api/health/db`，连不上时给出警告，但不让部署失败 |

**排查顺序**：线上登录异常时，先 `curl https://<frontend>/api/health/db`。返回 503 时，再执行
`az postgres flexible-server show -g rg-aiinterview-public-swedencentral -n psql-aiinterview-public --query state`。
如果是 `Stopped`，手动启动或运行 `infra/azure/scripts/ensure-db-running.sh <resource-group>` 都可以。
