# 后台任务与数据库锁

本文说明后台任务（job）现在怎么运行、有哪些锁以及各自锁的是什么，以及为什么任务进程放在一个**单独的容器**里。设计和实施过程见 [`planning/spec-jobs-and-scale-out.md`](planning/spec-jobs-and-scale-out.md)；数据库侧的细节见 [`database.md`](database.md) 第八节。

上线版本：v0.67.0.0（任务表与任务进程）、v0.68.0.0（管理后台「后台任务」页）、v0.68.1.0（3 个 worker × 最多 2 个副本）。2026-10-11 已在线上验证。

## 一、任务怎么运行

### 1. 两个容器，各做一件事

后端 Container App 的每个副本里有两个容器，用同一个镜像、同一套环境变量，只是启动命令不同：

| 容器 | 进程 | 职责 |
|---|---|---|
| `backend` | uvicorn，3 个 worker 进程 | 接请求、处理语音 WebSocket。遇到耗时的工作只往 `jobs` 表插一行，**自己不执行** |
| `jobs` | `python -m app.jobs.runner`，1 个进程 | 专门从 `jobs` 表领取任务并执行 |

两个容器都设了 `JOB_RUNNER_MODE=off`：Web 进程不跑任务，任务进程也不会在领取流程之外「顺手」启动任务。

### 2. 一个任务的生命周期

1. **排队：** 请求进来，Web 进程插入一行，状态为 `queued`。
2. **领取：** 任务进程每秒查一次排队中的任务，用一条带条件的 UPDATE 把它改成 `running`，同时写上自己的名字和租约到期时间。
3. **执行：** 每 15 秒续一次租约（每次续 60 秒）。
4. **结束：** 写回 `succeeded` / `failed` / `cancelled`，以及结果或错误。

候选人提交评分后看到的进度，不再由 Web 进程自己打分产生：它每秒读一次任务行上记录的进度，按原来的 NDJSON 格式推给浏览器，前端没有改动。管理员「生成报告」和候选人提交是**同一个任务**：后来的一方跟随已有的任务，不会重复评分。

### 3. 任务类型

| 任务 | 做什么 |
|---|---|
| `score_interview` | 给一场面试打分 |
| `sop_build` | 把一份 SOP 转成章节并生成检索向量；完成后如需要，再排一个摘要任务 |
| `sop_summary` | 起草一份 SOP 的摘要 |
| `sop_backfill` | 启动时为所有需要转换或摘要的文档排任务，并补齐检索向量 |
| `citation_run` | 重新定位一个题库的 SOP 引用 |
| `persona_sync` | 把默认面试官同步到 Foundry |

**唯一不走任务的：候选人录音上传。** 录音数据只在接语音的那个 Web 进程的内存里，别的进程拿不到；重启时丢失录音是已接受的取舍。

### 4. 并发

- 每个任务进程同时最多跑 4 个任务（`JOB_RUNNER_CONCURRENCY`）。
- SOP 转换和摘要在**每个任务进程内**一次只跑一个：LibreOffice 不能用同一份配置同时开两个会话。
- 最多 2 个副本，就最多 2 个任务进程。它们可能同时各转一份**不同的**文档，但同一份文档不会同时转两次（见第二节第 1 种锁）。

### 5. 出错与重启

| 情况 | 处理 |
|---|---|
| 进程死了（部署、重启、崩溃） | 租约 60 秒后过期，任何一个任务进程都会把它重新排队，最多尝试 3 次 |
| 任务自己报错（比如模型名配错） | 直接失败，**不重试**。评分本身已经对每道题有重试，任务层再重试 3 次只会让候选人多等几分钟 |
| 正常停机 | 任务进程把手上的任务交还队列，不消耗尝试次数，下一个进程马上接手 |
| 没有任务进程领取评分任务 | 排队 10 分钟后，候选人得到 503「评分还没开始，请稍后再试」，任务仍保留在队列里 |
| 续租时连不上数据库 | 在租约有效期内重试；超过之后停止执行，因为别的进程可能已经接手，绝不让同一个任务同时跑两份 |

### 6. 不同环境下的模式

| 模式 | 用在哪里 | 行为 |
|---|---|---|
| `off` | 线上 | Web 只排队，`jobs` 容器执行 |
| `embedded`（默认） | 本地开发、e2e | 任务在 Web 进程里跑，排队后立即开始，另有轮询兜底 |
| `inline` | pytest | 请求自己把任务（含重试）跑完再返回。原因：测试用的内存数据库只有一个共享连接，并发会话的回滚会撤销另一个会话尚未提交的领取 |

真正的并发行为（抢任务、租约过期、取消、停机交还）由 `backend/tests/test_jobs.py` 在文件数据库上测试，每个会话有独立连接。

### 7. 管理后台「后台任务」页

列出所有任务，最新的在前。默认只显示排队中、运行中和失败的任务，可按状态、类型筛选。失败或已取消的任务可以重试（引用定位任务重试时会新建一次运行），排队中或运行中的任务可以取消（运行中的任务在下一次续租时停止，约 15 秒内）。有任务在进行时，每 5 秒刷新一次。

## 二、有哪些锁，各自锁什么

**跨请求、跨进程的防重现在都在数据库里。**

| # | 锁什么 | 怎么实现 | 防止什么 | 替代了原来的 |
|---|---|---|---|---|
| 1 | **同一件工作只有一个活任务**（同一场面试的评分、同一份文档的转换） | `jobs` 表的部分唯一索引 `uq_jobs_live_target`：`(kind, target_id)`，只对 `queued` / `running` 的行生效 | 双击、刷新、两个进程同时提交，结果评两次分，或者同一文档的章节被两次转换写乱 | 进程内的 `_SCORING`、`_BUILDS`、`_BUILD_LOCK`、`_CONVERTING`、`_DRAFTING`、`_SUMMARY_LOCK` |
| 2 | **谁来执行这个任务** | 带条件的 UPDATE：`... WHERE id = ? AND status = 'queued'`，改到行的一方才拥有它 | 两个任务进程领到同一个任务 | （原来只有一个进程） |
| 3 | **执行权保持多久** | `jobs.lease_until` 租约，每 15 秒续期 | 进程死后任务永远卡在 `running` | 引用定位原来靠「10 分钟没心跳就算中断」来猜 |
| 4 | **一场面试同一时刻只有一次 judge（判断）调用** | `interview_sessions.judge_lease_until`，带条件的 UPDATE 拿到才调 LLM，否则返回 409，前端当作「先等等」；30 秒自动过期 | 两个请求同时为同一道题问 LLM 要不要插话 | 进程内的 `_JUDGE_IN_FLIGHT` |
| 5 | **启动初始化**（种子数据、客户题库导入） | PostgreSQL 会话级 advisory lock，用一个专用连接从头持有到尾（`app.db.boot_lock`、`scripts/with_boot_lock.py`）；SQLite 上不做任何事 | 3 个 worker × 2 个副本同时启动，都发现「默认题库不存在」，各建一个 | （原来只有一个进程） |
| 6 | **数据库迁移** | Alembic 的 `pg_advisory_xact_lock`（这次之前就有） | 两个副本同时改表结构 | — |

以前就在数据库里、这次没动的保护：

- 答题回合的 `turn_version` 乐观锁：提交答案时带版本号做条件 UPDATE，两份不同的答案不能驱动同一个回合。
- 唯一索引：一个候选人同时只有一场进行中的面试；每个题库同时只有一个 running 的引用定位；面试官不重名；每道题只有一个默认评分标准。

**配置保存不是锁，是同步：** 每个进程记住自己最后应用过的主配置。语音连接建立时、每个任务开始前、以及每 30 秒，都会对比一次数据库；发现别的进程保存过，就重新应用（`config_overlay.ensure_current`）。

### 为什么用「租约行」，而不是到处用 advisory lock

- advisory lock 绑定在**某一个数据库连接**上，和连接池配合不好：连接被还回池里时锁可能还挂着，或者被别的请求拿走。
- SQLite 不支持它，而开发和 CI 都用 SQLite。
- 租约行本身带过期时间：进程崩溃后锁自己失效，不需要人工清理。

所以只有「从头到尾占着一个连接」的启动初始化用了 advisory lock，其他都用带条件的 UPDATE 加过期时间。

### 仍在进程内、但不影响正确性的

1. **限流，不是防重：** 任务进程里「最多 4 个并发」的计数，以及「SOP 转换一次一个」的进程内锁。同一份文档不被重复处理，靠的是第 1 种锁。
2. **缓存：** 管理员密码校验缓存、检索向量的查询缓存、Voice Live 模型探测缓存、模型客户端注册表。每个进程各一份，最坏是多算一次，不会算错。
3. **前端的数字人限流记录：** 存在浏览器里，和后端进程数无关。

### 尚未处理

- **数字人并发上限 5 个，是整个 Azure 资源级别的限制。** 后端没有全局计数，各进程各看各的。要做「排队等数字人」，计数需要放进数据库（TODOS 里的待办）。
- **judge 租约的释放是无条件的。** 理论上，一次 judge 调用如果超过 30 秒，会清掉别人的租约；judge 本身 10 秒就超时，实际不会发生。

## 三、为什么任务进程放在单独的容器里（2026-10-11 讨论，决定保留）

一个容器里跑两个进程也能做到：在 `entrypoint.sh` 里把任务进程放到后台启动，再启动 uvicorn。选两个容器（sidecar），原因如下。

### 1. 资源隔离：这是拆进程的初衷

拆进程是为了**不让耗时工作影响正在进行的语音面试**。「不同进程」只解决了「不共用一个事件循环」，还没解决「不抢同一份 CPU 和内存」。Container Apps（底层是 Kubernetes）的 CPU 和内存上限是**按容器**设的。

- **CPU：**
  - 同一个容器：两个进程共用一份配额。LibreOffice 转大文档或评分时把 CPU 吃满，Web 进程被限速，语音照样卡。
  - 两个容器：Web 固定 2 vCPU / 4 GiB，任务 1 vCPU / 2 GiB，任务进程最多只能用满自己那 1 vCPU。
- **内存：**
  - 同一个容器：LibreOffice 遇到大文件冲到上限触发 OOM，整个容器被重启，**所有正在进行的语音面试一起断掉**。
  - 两个容器：只有 `jobs` 容器被重启。语音不受影响，被打断的任务等租约过期后自动重新排队。

### 2. 进程挂了，有人把它拉起来

平台监控和重启的单位是**容器**，不是进程。

- **同一个容器：** 镜像里的 `tini` 只负责回收僵尸进程，不负责重启。任务进程崩了：
  - 健康检查只看 uvicorn 的 `/health`，平台不知道任务进程没了；
  - 任务一直排队没人跑，候选人要等 10 分钟才看到「评分还没开始」。
- **补救办法有两种，都不理想：**
  - 装一个进程管理器（如 supervisord），镜像和配置都变复杂；
  - 写成「任一进程退出就让整个容器退出」，结果任务进程一崩，就连带重启 Web 和语音。
- **两个容器：** 任务进程退出，平台只重启 `jobs` 容器。

注意：`jobs` 容器用 `args` 而不是 `command` 指定启动命令，这样会保留镜像的 `tini` 入口，LibreOffice 留下的子进程会被回收，不会变成僵尸进程。

### 3. 日志和排查分开

上线验证时，用 `az containerapp logs show --container jobs` 只看任务进程的日志，并进入 `jobs` 容器查数据库，完全不打扰 Web。放在一个容器里，两边的日志会混在一起。

### 4. 启动流程互不干扰

- **Web 容器：** 走 `entrypoint.sh`，跑数据库迁移、导入客户题库，再启动 uvicorn。
- **任务容器：** 直接启动 runner，等数据库迁移到最新版本后才开始领任务（`app.db.wait_for_schema`）。

### 代价

| 代价 | 说明 |
|---|---|
| 资源是预留的 | 任务容器即使空闲，也占着 1 vCPU / 2 GiB 并计费；一个容器两个进程可以共用，总配额更小 |
| 扩缩跟着副本走 | 一个副本固定带一个任务进程，不能单独扩任务进程；目前规模下无所谓 |
| 部署要更新两个容器 | 部署流程里对两个容器各调用一次更新（先 `jobs` 再 `backend`），每次部署多一个 revision、多一次短暂切换 |

### 考虑过的其他做法

| 做法 | 结论 |
|---|---|
| **一个容器两个进程** | 更省、更简单。代价是任务进程崩溃或内存超限会把 Web 一起重启，正在进行的语音面试会断。如果将来更看重成本，可以改成这样：总配额约 2.5 vCPU / 5 GiB，用 `wait -n` 实现「任一进程退出就退出容器」 |
| **独立的 Container App** | 可以独立扩缩、独立部署，但身份、环境变量、密钥、网络都要再配一套，部署流程也要再加一个应用。目前 demo 规模下过重 |
| **两个容器（当前）** | 在隔离和复杂度之间折中，**2026-10-11 决定保留** |

## 四、连接数

每个进程一个连接池（`DB_POOL_SIZE` / `DB_MAX_OVERFLOW`，线上都是 5），任务进程也算一个。

- **平时：** (3 个 Web worker + 1 个任务进程) × 10 × 2 个副本 = 80。
- **版本切换时：** 新旧两个 revision 短暂共存，最多 160。

这仍远低于 PostgreSQL B2s 的 414 个用户连接。注意 Azure 在服务器**创建**时才按规格计算 `max_connections`，之后改规格不会自动改它，所以 B2s 的 429 是手工设置的。
